## Phase 1 — Core I/O and model

### 1.1 Image buffers and tiling

- [x] `Image<T>` over u8, u16 and f32 with 1 to 4 channels, a row stride and a color-space tag (linear or sRGB-encoded, optional ICC profile), done in 0.3; the rest of 1.1 builds on it
- [x] Conversions between sample types and between encoded and linear, vectorized and parallel with rayon; stacking math in linear f32 (`florastack_core::convert`: exact round trips for every `u8` and `u16` value, sRGB through tables or a branch-free power function)
- [x] Tiled view: overlapping tiles stitched back with feathered seams (`TileGrid`, with `stitch_with` holding two rows of tiles at a time)
- [x] Disk-backed tile cache: `TileCache` with LRU eviction and a RAM budget over a `TileStore` (`TempFileStore`: temp files, plain file I/O), so 500+ frames at 60 MP never need to be resident
- [x] Basic ops: Lanczos3 resize, separable Gaussian blur with a running-sum approximation for large radii, Sobel, Laplacian, and bilinear and bicubic affine warps (`florastack_core::ops`)
- [x] Property tests (proptest) for conversions and tile round trips; criterion benches for blur and warp on a 24 MP image
- [x] The synthetic generator's private exact blur and bicubic warp (`crates/core/src/testutil/ops.rs`) replaced in the generator by the public ops, which match them bit for bit, and kept as the tests' oracle

### 1.2 LightCraft dependency, codecs, metadata and color *(plan first)*

- [x] EXIF, IPTC and XMP read and carried over from a chosen source frame, with the software tag and the frame count in XMP
- [x] Embedded ICC profiles kept (sRGB assumed without one), with output in the input profile or a wide working space (ProPhoto RGB by default, or Rec. 2020)
- [x] EXIF orientation honored or ignored by option (or forced), with `Orientation` and `Image::oriented` in florastack-core
- [x] Tests: round trip per format and bit depth, metadata, orientation; PngSuite, TIFF, WebP and OpenEXR fixtures fetched by `cargo xtask corpus`, and by CI before the tests
- [x] Images whose ICC profile has another curve than sRGB's are linearized through the profile (`florastack_core::convert` knows linear and sRGB only, and carries the profile over unchanged)
- [x] `cargo xtask corpus`: archive entries (PngSuite ships as one `.tgz`) and a place for format fixtures beside the stacks
- [ ] Open a linear DNG written by FloraStack in Lightroom Classic or Adobe Camera Raw, and check it with the DNG SDK's `dng_validate`: the tests read it back with LightCraft's RAW decoder only, and the DNG specification couldn't be downloaded while the writer was built
- [x] The LightCraft pin moved to release 0.20.0, which has quick-xml 0.41 (storytold/lightcraft#1464), and the two advisory ignores dropped from `deny.toml` and `.cargo/audit.toml`; `lightcraft-raw` now brings `craft-crw` from a second git source, `storytold/craft-libs`, which `deny.toml` allows
- [x] 12-bit TIFF: the tiff crate (0.11.3) still rejects samples of 9 to 15 bits, so `florastack-codecs` reads them itself (`decode/packed.rs`): the layout from lightcraft-tiff's IFDs, strips or tiles that are uncompressed, LZW, Deflate or PackBits, gray (either polarity) and RGB with extra samples, scaled to 16 bits; planar files, predictors, signed and float samples and `FillOrder` 2 are reported as unsupported. The tests make their files from the specification (`crates/codecs/tests/packed.rs`)
- [ ] A real 12-bit TIFF from a scanner or a microscope camera among the format fixtures: none is pinned, so the reader has only met files made by its own tests
- [x] Streaming TIFF and DNG writers that take the image a band of rows at a time (`florastack_codecs::write_to` from a `RowSource`, `write_file_from`): each band of about 32 MB is converted to the output's depth and profile, its strips or tiles compressed in parallel and written, and the IFDs follow the image data (`encode/container.rs`, the layout of lightcraft-tiff's writer, whose files it matches byte for byte), so neither the converted image nor the file is whole in memory; a file is BigTIFF when its samples could pass 4 GiB, decided before the first strip. `output.save` and `export.run` stage their image files this way, and take the sidecar's hash from the staged file
- [ ] The engine still holds an output whole while it is exported (the cached result, with its strokes, adjustments and annotations rendered as one image): render it a band at a time into `write_to`'s `RowSource`, so that an export's memory doesn't grow with the output
- [ ] The project cache's TIFF files (`florastack_engine::project::write_image`) are still encoded in memory and stored from their bytes: `CacheWriter` hashes what it is given in order and can't seek back to a TIFF's header; hash the finished file instead, as `Publication::stage_image` does, and read cache files a band at a time too
- [x] Float DNG and a preview IFD in the DNG writer: 32-bit float `LinearRaw` (white at 1, values beyond it kept with the extended range, `DNGBackwardVersion` 1.4), uncompressed or Deflate with the floating-point predictor (`DngCompression::Deflate`; lossless JPEG stays for 16-bit files, and the output settings take either for the other at the other depth), and by default a preview: IFD0 an uncompressed 8-bit sRGB picture of at most 1024 pixels a side, box-filtered from the bands as they are written, with the raw image in its sub-IFD, as Adobe lays DNG files out (`dng_preview`, **Embed a preview** in the Export tab)
- [ ] A JPEG-compressed preview in the DNG writer (the uncompressed one takes up to 3 MB), and a full-size one for converters that show it while they develop
- [x] The `exr = "=1.74.0"` pin lifted: exr 1.74.3 no longer pulls in `paste` (RUSTSEC-2024-0436) through `pulp`, and DWA-compressed files are read (a test writes DWAA and DWAB files with the exr crate and reads them back)

### 1.3 RAW import through LightCraft

- [x] `RawDecoder` trait in florastack-raw, implemented with LightCraft's raw crate (`LightCraftRaw`), decoding into plain `RawFrame` data (normalized samples, the color filter array, the DNG color model) that another decoder could produce
- [x] LightCraft's coverage (DNG, CR2, CR3, ARW, NEF, RAF Bayer and X-Trans, RW2/RWL, PEF, uncompressed ORF and SRW), with a clear error suggesting DNG or 16-bit TIFF for anything else (`RawError::Unsupported`)
- [x] `RawDevelop` to linear, scene-referred f32 RGB (Rec. 2020): white balance (as shot, auto, temperature and tint), fast and high-quality demosaic (X-Trans included), highlight reconstruction, exposure, lateral chromatic aberration and light noise reduction, with no tone curve or look; LightCraft's develop code from its raw and pipeline crates
- [x] Lens distortion correction off by default (`DevelopSettings::lens_distortion`; the file's vignetting correction still applies)
- [x] One `DevelopSettings` per stack, resolved once on a reference frame (`RawDevelop::new`, `Resolved`) so that every frame gets the same white and corrections, with serde for the project file and partial presets; storing it in the project is 1.4's (below)
- [x] 16-bit TIFF and DNG imported unchanged: demosaiced (`LinearRaw`) DNG files by florastack-raw, TIFF and the other image files by florastack-codecs, the choice made in `florastack_engine::frames` (no layering change)
- [x] Tests: one file per format (twelve CC0 files from raw.pixls.us, the `raw` fixture set, cached in CI), identical settings give identical output, preview and final demosaic agree on smooth regions, output stays linear (a gray step wedge)
- [x] `lightcraft-raw`'s `jxl` feature turned on: JPEG XL compressed DNGs (DNG 1.7) through jxl-oxide, pure Rust
- [ ] Camera color: fourteen of the sixteen pinned non-DNG files (all but the two Canon EOS R6 files and the Fujifilm X-S10) have no color matrix in LightCraft's low-level crates (`ColorSource::Fallback`, camera RGB taken for sRGB, flagged `DevelopWarning::ApproximateColor`); at release 0.20 those crates hold the 52 spectral matrices and one chart-measured camera (the EOS D60), and LightCraft's per-file camera-look fits and bundled profiles still live in its engine crate. Find a permissible source of matrices for the popular bodies, or ask LightCraft to move its fits into a low-level crate
- [x] More samples, for the paths the first twelve files don't reach: a lossless CRX CR3 (the first one is C-RAW; the files' `CMP1` boxes say which), CRW (an EOS D30), MRW, ERF, an uncompressed NRW and RWL, six more CC0 files from raw.pixls.us in the `raw` fixture set, which now takes about 186 MB
- [ ] Samples still missing: Hasselblad 3FR or FFF (the smallest CC0 files are 51 and 67 MB) and Mamiya MEF (raw.pixls.us has none under CC0)
- [ ] Cameras whose color filters aren't red, green and blue: LightCraft reads the Canon PowerShot G1's CRW files, whose sensor has cyan, yellow, green and magenta filters, as an RGB Bayer mosaic, so their samples decode and their colors are wrong (the fast and the output demosaic disagree by 13% on smooth blocks of raw.pixls.us file 2073, against 3% at most on every other file). Refuse or flag such cameras, or report it to LightCraft
- [x] Reduced-size development straight from the mosaic (`RawDevelop::develop_reduced`, `FrameReader::read_reduced`): one pixel per block of photosites, each channel the mean of the block's samples of its color, then the same white balance, highlight reconstruction, color and exposure, with no demosaic; used for the filmstrip's thumbnails (`filmstrip.update`, when no defect mask is to be inpainted), for finding stacks (`project.findStacks`) and for the viewer's thumbnails. On the pinned files each channel's mean is within 1% of the full development's
- [ ] Quarter-scale stack previews (3.1) from reduced frames: `stack.preview` still develops every RAW frame whole with the fast demosaic and reduces it afterwards, because its warps are planned on full-size frames
- [x] `RawDecoder::decode` no longer decodes ORF files twice: LightCraft's header probe unpacks their samples, so the size is checked on the decoded frame alone (their samples are no more than the file holds). The header check stays for PEF, whose compressed files it reads cheaply; an uncompressed PEF without crop tags is still unpacked twice
- [x] Color noise reduction on linear data: LightCraft's chroma filter divides color by luminance, which is zero or below in the noise of a sensor's shadows, and on a dark frame (the pinned Canon EOS 5D Mark III DNG) it left 214 000 samples above twice white, up to 83; `florastack-raw` now blurs each pixel's color difference from its luminance instead (`reduce_color_noise`), which keeps every pixel's luminance, clips nothing and leaves that frame's mean where it was. Frames developed with color noise reduction get a new fingerprint
- [x] A truncated RAW file, such as one a camera is still writing, is a `Malformed` error like a damaged one, so the watch folder (4.2) waits: `watch.run` takes a file only once its size and modification time have stood still for `settleMs` and it decodes, and reads it again later otherwise
- [x] `cargo check -p florastack-raw --target wasm32-unknown-unknown`, with LightCraft's pipeline, develop and raster crates (7.3): they build for the browser, threads and all, and CI's `web` job lints them for it (`cargo xtask web --clippy`)

## Phase 2 — Alignment

### 2.1 Frame alignment *(plan first)*

- [x] Per-frame shift, scale, rotation and brightness gain relative to a master frame, each term switchable (`StackAligner`, which takes the frames one at a time and holds three prepared frames whatever the stack's length, and `align_frames`; `AlignSettings` with serde and a JSON schema; a term that is off stays exactly 0 or 1)
- [x] Coarse-to-fine ECC with a phase-correlation first guess, on band-passed luminance rather than gradient magnitudes: a linear band-pass keeps a symmetric defocus from shifting detail, and the gradient magnitude's apparent motion between frames focused apart was about twice as large. ECC gets a defocus term (the template's Laplacian, projected out) and Tukey weights; frames are chained to their neighbors, optionally refined against the master (which helps shallow stacks: 0.004 to 0.008 px instead of 0.008 to 0.019 without defocus, and hurts deep ones); frames above 2048 px are aligned at that size
- [x] Limits per term (shift in percent of the frame, scale change, rotation); alignments that hit a limit, score low or find no match are flagged and, by default, rejected, the chain going around them; repeating patterns are flagged from the peaks of the plain correlation, and the whitened one picks the period nearest the expected shift
- [x] Brightness gain from robust statistics of low-pass content: the median ratio to the master on a 64-pixel low-pass, within 0.04% of the truth without defocus
- [x] Synthetic-stack accuracy tests (`crates/align/tests/accuracy.rs`, 16 frames, three seeds, master first or in the middle), per stack: at most 0.3 px on noisy, dusty stacks (measured 0.18 to 0.21), as planned; at most 0.15 px on clean stacks (measured 0.09 to 0.12) instead of 0.1, because defocus alone moves the synthetic content by 0.06 to 0.12 px (the test's documentation explains why); and at most 0.05 px on stacks moved but not defocused (measured 0.008 to 0.019), which measures the aligner itself

### 2.3 Dust, hot pixels and movement

- [x] Defect stage before warping (`DefectMask`, `DefectDetector`, `inpaint`): a user mask (an image of black spots on white, the frames' size) or one detected from the frames, inpainted in every frame by pull-push before it is aligned, and saved for reuse. Dust is darker than its surroundings on every side by the same factor in every frame: each pixel's ratio to the sixth darkest of 16 samples on a ring around it (12 px or 0.5% of the frame), whose mean and spread over the frames pick steady cores, grown by hysteresis, made symmetric about their center and grown by their radius; hot pixels are brighter than their neighbors two pixels away in 80% of the frames. At most 32 frames are read; the detector holds 10 bytes per pixel of the dust plane (half resolution above 4096 px) and 1 per frame pixel. In the engine: `defects.detect` (a job), `defects.import`, `defects.export` (an 8-bit PNG to edit), `defects.clear` and `defects.info`; the mask is the project's `defects` map, a lossless TIFF with its summary as cache key; `align.run` and `align.sortByScale` inpaint it, and detect one first when `detect_defects` is on (off by default) and the project has none, in the same undo step
- [x] Movement detection (`Motion`, `MotionMap`, `Flag::Moved`): each frame's residual motion against the neighbor it was aligned to, per cell (at least 8 px, at most 64 cells a side, on a level of at most 1024 px), by pyramidal Lucas–Kanade with the gain and defocus terms of the global alignment, on the band-pass pyramids alignment prepares anyway. A cell is measured when it has detail in two directions and correlates at least 0.8 once displaced; it moved from `min_motion` (2 px by default, and at least ¾ px of its level); moved cells count only where the frame is among the sharpest (its focus energy at least half the sharpest frame's), since elsewhere the stack takes that part from other frames; a region of two cells flags the frame, never rejects it. The project keeps each frame's score, largest displacement and regions (with their median displacement) in its report (format version 3), shown by `align.info`, `project.frames` (`motionScore`) and `filmstrip.list`
- [x] Filmstrip data API (`thumbnail`, `aligned_thumbnail`; `filmstrip.list`, `filmstrip.update`): every frame's preview as shot (developed and inpainted, at most 512 px, JPEG) and aligned onto the output's canvas of the framing set, keyed by what they were made from (the frame's contents, the develop settings and the defect mask; the preview, the transform and the canvas), so that the list tells current previews from stale ones. `align.run` writes them as it reads the frames, in its undo step; `filmstrip.update` (a superseding preview job, no undo step) makes the stale ones, the aligned ones from the previews without reading a frame. - [x] Tests: no dust trails after masking (`crates/align/tests/defects.rs`: in a max-contrast stack of the masked frames, the darkest trail of dust on a defocused backdrop keeps 0.999 to 1.000 of the light of the same frames without dust inpainted alike, against 0.49 to 0.62 unmasked; dust anywhere, the subject's edges included, keeps 0.92 to 0.995, at least half its darkening removed; clean stacks, moving or still, have nothing masked); injected movement is flagged (`crates/align/tests/motion.rs`: a patch of the subject moved in one frame flags it and the next, a subject that moves once flags one frame, movement behind the focus flags nothing, and clean, noisy and inpainted dusty stacks flag no frame); `crates/engine/tests/defects.rs` and `filmstrip.rs` run it all from frame files

### 2.4 Alignment corrections *(plan first)*

Each frame's color and tone matched to the master's, and the geometry beyond a similarity, in rough order of value for the effort. Every color and tone correction is measured on broad tones only, as the brightness gain is: a blurred frame has less local contrast than a sharp one, and that difference is what stacking picks frames by.

- [x] White balance: one gain per color channel on top of the brightness gain, measured as that gain is (the median ratio on each linear channel low-passed to 64 pixels, against the master, leaving out the dark and the clipped) and balanced so it changes color and not brightness (`AlignSettings::white_balance`, off by default; `crates/align/src/white_balance.rs`), for JPEG stacks shot with automatic white balance and light that changes color. Stored in the project (format version 5), reported by `align.info` and the alignment CSV, applied wherever the brightness gain is (CPU and GPU stacking, previews, retouch sources, exported aligned frames); the app's **White balance** toggle, `--align white-balance`. On moved, defocused, noisy synthetic stacks the gains are within 0.15% of the truth, and within 0.23% of 1 when frames differ only in focus (`crates/align/tests/white_balance.rs`); stacking frames whose white balance changes, the mean deltaE against the master's colors falls from 5.29 to 1.78 (`crates/engine/tests/white_balance.rs`)
- [ ] Contrast: a gain and an offset, for haze, flare and shadows lifted differently from frame to frame. Tried and set aside: fitted on the same low-passed planes, on synthetic frames that differ only in focus, the slope rose with distance from the master (up to 4% at 1920 px, 7.5% at 320 px), from depth edges, where a blurred near edge spreads over a background of another tone; without depth edges it stayed within 0.3% of 1. The low-pass also narrows the tones, so slope and offset trade off and extrapolate badly to dark tones. Needs a measure that leaves out where the frames' sharpness differs, a fallback to the gain when the tones are too narrow, or a check across two scales, and a real stack whose tones change to judge it
- [ ] Tone curve: a smooth, increasing curve from each frame's broad tones to the master's, for JPEGs, whose tone curve makes a change of exposure nonlinear (RAW frames, developed linear, need only the gains). Tried with contrast (brightness transfer function, Grossberg and Nayar 2003, made increasing by pool-adjacent-violators) and set aside for the same reasons: errors of 14 to 38% on frames that differ only in focus
- [ ] Vignetting that changes with focus: a smooth brightness map per frame (a low-order polynomial over the frame), so that the corners don't blotch
- [x] Transforms smoothed along the stack: on a rail or a steady focus ramp, shift and scale change smoothly from frame to frame; fit a curve through them and flag the frames far from it. Flagged, not smoothed (`trend.rs`, `Flag::OffTrend`, `align.run`'s `offTrend`): each frame's terms are predicted by a straight line through up to three frames that aligned on each side, the frame left out, and a frame is off the trend when the difference moves its corner by at least 1 pixel of the working resolution and 6 times the stack's median residual (fitted without that frame, which would pull its neighbors' predictions along), the worst frame taken out and the rest fitted again, at most a quarter of them. A frame knocked by 3 px out of a breathing synthetic stack is flagged alone, at the middle or either end; stacks whose frames wander at random by up to 1.5 px, and every accuracy stack, have none (`crates/align/tests/trend.rs`). On the five local stacks the only frames flagged are the first of the cricket and the mosquito, the frame the camera shoots first at the focus point, out of the order of focus, and `crates/engine/tests/corpus.rs` checks that a frame off the trend is one out of order. Snapping a frame onto the curve is left undone: the drift found on the synthetic stacks (the next item) is a smooth bias that a curve would keep
- [ ] Less drift along the chain: match each frame against frames two or three away as well as its neighbor, and solve every transform together (the synthetic stacks drift 0.5 to 2.5 px, 3.5). Tried and set aside: on the quality runner's layered stacks, whose frames don't move, the drift is a bias, not noise. Each link's error is mostly in scale, of the same sign over long runs of links (-1600 to -4700 ppm, 0.5 to 1.4 px at a corner, where a blurred layer grows as the focus leaves it and the scale term takes its growth for magnification), its shift 0.01 to 0.1 px. Links two and three frames apart carry the same bias, so a least-squares solve over all the links (weighted by score, each term on its own) moved the mean error by -10% to +23% (from separate pairwise alignments: clean 0.73 to 0.89 px, noisy 2.08 to 2.08, 48 frames 11.6 to 10.5) against 0.60, 1.55 and 3.44 px for the chain from the middle frame that alignment makes. What would help is the safeguard contrast needs (above): measuring the transform where the two frames are about as sharp, leaving out where one frame's blur is growing. Refining against the master (`refine`) made two of these stacks worse (0.60 to 1.84 px, 3.44 to 4.00) and the noisy one better (1.55 to 1.14)
- [ ] Lateral chromatic aberration that changes with focus: a scale of the red and blue channels against green per frame, for JPEG stacks (RAW frames get the develop step's correction)
- [ ] Distortion that changes with focus: one radial term per frame, for wide-angle stacks
- [ ] Perspective: a homography for handheld stacks whose camera tilts, and microscope stages that aren't level, with care not to fit noise
- [ ] The region to align on: the user marks the subject, or leaves out a moving background or sky
- [x] The master frame chosen by hand: `align.setMaster` (an undoable job) records the frame in the project (`Project::chosen_master`, `Edit::SetChosenMaster`, format version 9) and, when the project holds an alignment that fits it otherwise, rebases it onto that frame without reading a frame (`florastack_align::order_stack_on`), the aligned previews made again from the frames' previews, as reordering does (2.2); every later alignment keeps it while the frame is enabled and aligns (`align.run`'s `masterChosen`), and a disabled or rejected frame is refused. The master sets the brightness and color the frames are matched to and the pixel grid of wide and common framing; narrow framing keeps the narrow end's field of view and pixels whichever frame is the master. The frame list marks the master, and a frame's context menu makes it the master or lets the stack choose again. Rebased onto a frame chosen on a moving, breathing stack, the transforms are within 0.005 px of the truth relative to it (`crates/align/tests/ordering.rs`); `crates/engine/tests/align.rs` chooses before and after aligning, with the frames' files gone
- [ ] Local movement corrected rather than flagged: a smooth warp from the motion maps, for a swaying flower or a moving antenna, without mistaking a change of blur for movement

## Phase 3 — Stacking engines

### 3.1 Streaming framework and weighted average

- [x] Streaming method trait with progress, tiled for large images and deterministic: `Stacker` (`begin`, `add_frame`, `finish`) over `FrameSource`s, aligned frames that hand out any rectangle of the canvas with its coverage (`Patch`), so that the engine warps each frame tile by tile as it is read and the warped frame is never whole. Methods are `TileKernel`s run by `Tiled`, which keeps their accumulators tile by tile (`TileGrid`, tiles at least four times the overlap, the overlap twice the kernel's reach) in a `TileCache` with a memory budget (`Tiling`: 512 px tiles and 1 GiB by default, spilled to temporary files beyond), on each tile's inner region (its core grown by half the overlap, all the stitch reads), folds each frame a batch of tiles at a time in parallel, and stitches the tiles back at the end. The same bit for bit on one thread or many, and on one tile or many for blurs of up to 4 px (box blurs beyond round their running sums differently, below 1e-5); `add_frame` and `finish` report tiles done to their `Monitor` and stop at the next batch when cancelled, which ends the stack (`FrameProgress` maps a frame's tiles onto the whole stack's progress). `Method` makes stackers from settings, and `stack` drives one over frames in memory
- [x] Weighted-average method (`AverageSettings`, `WeightedAverage`): per pixel and frame, the Laplacian's energy of the frame's luminance (Nayar and Nakagawa's focus measure, the energy-of-Laplacian form of Pertuz et al.'s comparison) averaged over `radius`, scaled, floored and raised to `power`, blurred over `smoothing` and multiplied by the frame's coverage (its Laplacian left out where it would read an uncovered pixel), normalized and blended (contrast weights raised to an exponent, as Mertens et al.'s exposure fusion weighs its images, but blended directly). Defaults radius 3, smoothing 8, power 3, chosen on the two local camera stacks: a radius of 1 left a veil over the cricket's compound eye, and a smoothing of 3 dark dots and ghost outlines in the smooth background around the wasp
- [x] Quarter-scale preview mode for every method (`Preview`, `preview`, `Method::reduced`: frames and their coverage reduced by Lanczos3, lengths in the settings divided by 4)
- [x] Tests (`crates/stack/tests/average.rs`, `memory.rs`): beats the best single frame on SSIM, at a camera's scale (the scene enlarged three times, 720x540) with the defaults, 0.923 to 0.924 against 0.897 to 0.909 clean and 0.877 to 0.878 against 0.848 to 0.861 noisy, and at the generator's own (320x240) with settings for it, 0.961 to 0.962 against 0.894 to 0.895 and 0.878 to 0.879 against 0.869 to 0.870; frames warped onto the scene with their coverage, 0.951 to 0.956 against 0.887 to 0.890; uncovered pixels never smear (a frame's streaked edge beyond its coverage leaves no trace) and get alpha 0; the preview beats the best reduced frame (0.896 against 0.870) and is 38 dB from the full stack reduced; peak heap flat from 20 to 200 frames: 21.76 MiB for both (1520 bytes apart, a one-time allocation of the test harness), counted by dhat's allocator in a test binary of its own, with a 640x480 frame of 3.5 MiB in flight; plus tiles against one tile, threads, spilling to disk, cancellation, progress, hostile samples and settings
- [x] Engine commands (`commands::stack`): `stack.get`, `stack.set`, `stack.reset` (the `stack` preference group); `stack.average`, a heavy job that stacks the enabled frames of the stored alignment in its processing order on the canvas of the framing set, with each frame's brightness gain, and adds the output as one undo step (`Edit::AddOutput`, whose inverse removes it; linear f32 TIFF in the cache, with alpha only when some pixel is uncovered, and a JPEG preview); `stack.preview`, a superseding preview job at a quarter of the size, which changes nothing in the project. Neither locks the stacking settings, so that they can change, and previews follow, while a stack runs
- [x] Bench timing (`cargo xtask bench`, 16 threads): `stack/average/add-frame/6000x4000` 578 ms per 24 MP frame (41.5 Mpx/s), `finish` 530 ms, `preview-frame` 160 ms (the frame reduced to a quarter, then stacked), a whole 12-frame 1500x1000 stack 375 ms. At the defaults a tile's filters reach 42 px, so 512 px tiles compute on 1.76 times their core's pixels; larger tiles, with fewer of them at a time, could be faster
- [x] Checked on the two local JPEG stacks (`corpus/local`, not committed; release build, 20 MP camera JPEGs, 16 threads): the cricket (15 frames, sorted by scale) and the wasp (23) stacked in 16.4 and 23.8 s (`stack.average`, reading and decoding included; 41.9 s once for the wasp while the virus scanner was busy), previewed in 4.2 and 6.8 s, aligned in 15.2 and 15.3 s, at a peak working set of 1.29 and 1.26 GB for the whole run. Both are sharp from front to back where the sharpest single frame is sharp on a slice: the stacks' mean local sharpness is 1.26 and 1.52 times the sharpest frame's, and where some frame has strong detail (1.0% and 8.3% of the canvas) the stack keeps at least half of the best frame's sharpness at 99.6% and 89.8% of the pixels, the sharpest single frame at 1.4% and 10.7%. The wasp, which alignment flagged as moved in 18 of 23 frames, keeps faint ghost contours along its legs and wing
- [ ] Halos, veils and ghosts of the weighted average: a subject's blurred edge in the frames focused elsewhere veils a smooth background next to it (thin, at the defaults, on the local stacks), and a subject that moved leaves ghost contours. The pyramid and depth-map methods (3.2, 3.3) are the answer: on the local stacks 3.2's pyramid has none of the veils and halos, and none of the wasp's ghost outlines around its leg (3.2 above); 3.3's depth map leaves none over a smooth background, nor the wasp's ghosts, but a veil where an out-of-focus part crosses textured ground (3.3 below). The motion maps of 2.3 could also lower the weight of regions that moved, for both methods
- [x] The preview read and decoded every frame again (4 s for 15 frames of 20 MP): the session now keeps each frame's quarter-size copy, developed, inpainted and reduced, between previews (`ReducedFrames`, in memory, at most half the stacks' memory budget, keyed by the frame's file, development, defect mask and demosaic, dropped with the project), and `stack.threshold` and the depth maps of `adjust` and `retouch.mapFocus` share them. On the local JPEG stacks (release build, CPU, each preview a CLI run's command after the first), a preview after a change of a setting takes 0.17 to 0.84 s against 1.9 to 6.9 s for the first, which reads the frames (5.2)
- [x] Frames flagged out of focus are stacked unless disabled; their weights are low but they join the plain average of flat regions. Measured on the local stacks that have them (the cricket's farthest frame, the wasp's four frames between subject and background; release build, CPU): leaving them out never helped. The cricket's outputs are the same within 2 levels of 8 bits at 99.4% (average) and 99.9% (pyramid) of the pixels; on the wasp, the frames keep the smooth background smoother (its departure from a 33 px box blur 1.00 against 1.15 levels for the average, 2.21 against 2.32 for the pyramid; without them it shows faint bands) and leave the subject as it is. So they stay in by default, with no setting: the flag says where to look, and `project.setFramesEnabled` leaves out a frame that does harm
- [x] When the accumulators spill to disk, every frame read and wrote every spilled tile back (the least recently used tile was always the next one needed): the frames now take the tiles forward and backward in turn, as the GPU stacker already did, so that each starts with the tiles the one before ended with and reads back only those beyond the budget (on the test's 12 tiles with half of them in memory, 15 of the 24 tile planes a frame instead of all 24, `crates/stack/tests/average.rs`); the first frame makes each tile's state instead of `begin` writing empty ones beyond the budget to files, and `TileCache::take` counts in the cache's statistics, which `Tiled::cache_stats` shows
- [x] The output was encoded whole (a 240 MB f32 TIFF at 20 MP, with its bytes): the cache's images (`write_image`) are now streamed into their file by florastack-codecs' `write_to` a band of rows at a time, through a `CacheWriter` that seeks (it hashes the finished file once the writer has gone back to the header). The stacked image itself is still whole, as `Stacker::finish` returns it
- [x] GPU kernels for the weighted average (4.3): the weights (luminance, Laplacian energy, the two blurs, the power) and the accumulation, with `WeightedAverage::weights` and the tile fold as their CPU references (`crates/gpu/src/stack/average.rs`)

### 3.2 Pyramid method *(plan first)*

- [x] Laplacian pyramid and complex wavelets evaluated on the metrics and one chosen: the Laplacian pyramid (P. J. Burt and E. H. Adelson, 1983, with the 5-tap binomial kernel). In a throwaway prototype outside the repository, on layered synthetic stacks (below; 12 frames, three seeds), it scored SSIM 0.967 and halo 0.080 at a camera's scale on clean stacks, 0.956 and 0.080 on noisy ones, against 0.901 and 0.134 (clean) for complex wavelets after B. Forster et al. (2004) as focus-stack implements them (MIT, commit `0cd289e`), 0.956 and 0.082 (clean) and 0.922 and 0.083 (noisy) for the best wavelet variant (given the pyramid's window, blend and range limit), and 0.921 and 0.132, 0.894 and 0.133 for the weighted average; the wavelets were 2.5 to 4 times slower, need the image padded to a multiple of 128 pixels, and ring in flat dark areas. Of focus-stack only the range limit's idea is taken (ATTRIBUTION.md, NOTICE)
- [x] Streaming selection or soft blend of the highest-energy coefficients per level (`PyramidSettings`, `Pyramid`, `crates/stack/src/pyramid/`): at every level and position, the coefficients of the frame with the most local energy (the 5x5 binomial energy of the band's luminance, P. J. Burt and R. J. Kolczynski's salience), kept with that energy as a running best-so-far pyramid; the residual averaged over the frames, weighted by coverage; frames that cover part of the canvas reduced by normalized convolution (Knutsson and Westin), their choices weighed by the fourth power of their pooled coverage. Levels: `levels`, or by default `log2(short side) - 4` (5 at 720x540, 7 at 20 MP; the prototype scored 5 to 8 alike). The finest 3 levels are computed in tiles (a context of 48 pixels, reads aligned to 8 pixels so that every tile's levels lie on the canvas's lattice), the coarser ones and the residual on the whole canvas at 1/8 scale from each tile's share: `TileKernel` gained the hooks for it (`read_region`, `start`, `absorb`, `prepare`, state planes of `f32` or `u16`), and the weighted average runs on them unchanged. The same bit for bit on one tile or many, one thread or many, spilled or not (tested). State: 33 bytes per pixel for RGB (the weighted average's 16), plus 1/64 of the canvas per plane for the coarse part
- [x] Grit suppression: the finest level is a soft blend, each frame's coefficients weighted by its energy raised to `1 / grit` (`grit` 0.5 by default; 0 picks, as the other levels do; 0.25 to 1 blend). On the layered noisy stacks the blend has 0.0040 of flat-region noise against 0.0082 for picking and 0.0047 for the weighted average, for 0.0003 of SSIM on clean stacks. The prompt's consistency check of the fine level's choices against the coarser level's choice map was measured in the prototype (selecting where the two agree, blending elsewhere: noise 0.0047 against the blend's 0.0040 on noisy stacks, for 20 more bytes of state per pixel) and, with the user's approval, not built
- [x] Unclipped float result with a final local tone compression, and a "retain extended range" output: the stack's result is unclipped; `compress_range` (`Tone`: `compress`, the default, a shoulder whose knee follows the local maximum over 32-pixel blocks, so that only pixels near values above 1 change, and negatives to 0; `clip`; `keep`) brings it into range. `stack.pyramid` keeps the result from before tone compression as the output's `extended` map when that changes any pixel, and `output.save` writes it for `extended_range` at 32-bit float (TIFF, OpenEXR); codecs wrote float files with extended range since 1.2
- [x] Decisions on luminance (`Decisions::Luminance`, the default: one choice per position for all channels) or on all channels (`Decisions::Channels`). On the synthetic stacks, which have no chromatic aberration and colored texture at constant luminance, channel decisions scored higher (SSIM 0.971 against 0.960, mean deltaE 1.79 against 2.04 on the noisy native-scale stack); on the wasp they put blue-violet fringes along the wing and the yellow markings, so luminance stays the default
- [x] Limits on inversion halos: the range limit (`range_limit`, 1 by default), each channel of each pixel held within the range of the frames that cover it (after focus-stack's gray range limiting, per channel, its bounds kept as bfloat16 rounded outward): no pixel comes out darker or brighter than every frame. On the wasp, a luminance-only limit left 1.6% of the pixels out of range and a blue cast on the black thorax; per channel, 0.02% and neutral blacks (prototype, quarter scale). The prompt's limit on how far coarse choices may stray from the depth-consistent frame is built as `coarse_limit` (frames; at levels 3 and up; the depth-consistent frame is the one whose finest-level energy, pooled to the level, is largest there) and, with the user's approval, off by default: every form of it raised the halo metric on the layered stacks (0.082 against 0.080; with the true depth at levels 3 and up 0.099 against 0.077, at every level, an ideal depth map, 0.184), since at an occluding edge the frame in focus on the background is the one its out-of-focus foreground veils, and it showed no gain on the local stacks
- [x] Layered synthetic stacks with occlusion (`florastack_core::testutil::layered`: `scene::layered` and `generate_layered`): a backdrop (textured, or smooth on the right as macro backdrops are) defocused as `generate` does it, then discs and twelve crossing bristles at depths 0 to 0.55, each composited over what lies behind it with its alpha blurred by its own defocus (T. Porter and T. Duff's "over"; N. Asada, H. Fujiwara and T. Matsuyama's occluding-edge model), the truth the same at zero blur. They have the veils 3.1's stacks lacked. `generate` is unchanged (its steps after defocus are shared)
- [x] Tests (`crates/stack/tests/pyramid.rs`, `memory.rs`): on the layered stacks the pyramid beats the weighted average on SSIM and on the halo metric, by at least 0.03 of SSIM and to at most 0.75 of its halo at a camera's scale (720x540; 0.02 of SSIM on the smooth backdrop) and by 0.005 and 0.92 at the scene's own (320x240), clean and noisy, two seeds; measured SSIM 0.954 to 0.968 against 0.896 to 0.922 and halo 0.077 to 0.079 against 0.122 to 0.129 at the camera's scale, 0.963 to 0.976 against 0.929 to 0.948 and 0.072 to 0.073 against 0.119 to 0.122 on the smooth backdrop, and 0.957 to 0.973 against 0.887 to 0.959 and 0.054 to 0.056 against 0.066 to 0.069 at the scene's scale; noise, color shift, PSNR and the share out of range printed beside them. Plus grit suppression (noise below 0.6 of picking's and 1.1 of the average's), the range limit (every sample within the frames' range up to the bounds' rounding; frames brighter than white stack unclipped and compress into range), decisions (a red sharp only in one frame and a green only in another), the coarse limit, tiles, threads and spilling bit for bit, coverage (no smear, alpha 0), progress and cancellation, hostile samples and canvases of a pixel, settings, and the quarter-scale preview (SSIM 0.963 against the best reduced frame's 0.757, 43.2 dB from the full stack reduced); peak heap flat from 20 to 200 frames: 24.58 MiB for both on one thread (with several, the tiles in flight interleave their scratch differently from frame to frame: 46.46 and 47.00 MiB on 16 threads, nothing left after either)
- [x] Engine commands: `stack.pyramid`, a heavy job like `stack.average` (output method `pyramid`, its parameters with the levels used, one undo step; the summary gives the levels and how the range was brought in), `stack.preview` with `method` (`average` by default, so 3.1's calls keep working), and the `pyramid` table of the `stack` preference group (`stack.get`, `stack.set`, presets); `output.save` with `extended_range`; the engine re-exports `PyramidSettings`, `Decisions` and `Tone`

### 3.3 Depth-map method

- [x] Focus measure (modified Laplacian or Tenengrad) with a per-pixel best frame and a confidence (`DepthSettings`, `Estimator`, `FocusKernel`, `crates/stack/src/depth/`): pass 1 folds each frame's focus measure, the energy of the modified Laplacian (S. K. Nayar and Y. Nakagawa, 1994) of the luminance blurred over `radius` and averaged over `radius`, into a running record per pixel kept tile by tile (32 bytes a pixel): the sharpest frame, its focus and its neighbors' (the peak refined between frames by Nayar and Nakagawa's Gaussian interpolation), the runner-up (the most focus at least two frames from the sharpest, kept exactly as the sharpest moves), the floor (the least focus) and the sharpest frame's luminance. Confidence: the sharpest frame's local contrast less the runner-up's, `sqrt(peak) - sqrt(runner)`, and 0 where the focus curve never falls to a quarter of its peak (noise, a smooth surface). Measured in a throwaway sweep on synthetic stacks: without the blur before the Laplacian, the noise of camera-scale frames (twelve times the fine texture's energy) picked the sharpest frame at random (depth correlation 0.08 to 0.13 on noisy stacks), with it 0.56 to 0.69; a radius of 2 at camera scale was best of 1.5 to 4.5 (default 2); the mean of the other frames as the runner-up scored the same as the prompt's runner-up, kept
- [x] Edge-aware smoothing, with low-contrast regions filled from confident neighbors (`FocusStats::resolve`, `resolve.rs`, `filter.rs`): the confident pixels (at or above the threshold, not masked, and with a confident majority of their neighborhood) smoothed by the domain transform's recursive filter (E. S. L. Gastal and M. M. Oliveira, 2011) as a normalized convolution, guided by the cube root of the sharpest frames' luminance (`EDGE` 0.05: at 0.1 a smoothing of 16 px raised the halo metric from 0.09 to 0.12), and the rest filled by push-pull (S. J. Gortler et al., 1996) where fewer than half of a pixel's neighborhood is confident. All-or-nothing weights beat confidence-weighted ones in every synthetic case (layered clean SSIM 0.961 against 0.953)
- [x] Compositing from interpolated sub-frame depth that never alters color or contrast (`DepthMap::compositor`, `CompositeKernel`, `composite.rs`): pass 2 reads every frame again and takes each pixel from the two frames on either side of its depth, in proportion (weights `max(0, 1 - |i - depth|)` times coverage); where neither covers it (wide framing), the nearest covering frame's pixel. Every sample lies within the frames' range at its pixel (tested to 1e-6), and frames alike stack to themselves
- [x] Two-pass API: cached focus statistics, so a new threshold re-composites in under a second: `Estimator` (begin, add_frame, finish) gives `FocusStats` (depth, confidence, guide: 12 bytes a pixel); `FocusStats::resolve(threshold, smoothing, mask)` gives a `DepthMap` without reading a frame; its `compositor()` is a `Stacker` for pass 2; `depth_stack` runs all three on frames in memory. On 12 frames of 720x540 in memory, a new threshold takes 28 to 33 ms and its composite with it 60 to 68 ms (the fastest of three; tested under a second), and give the same depth map and composite as a whole new stack, bit for bit. At 24 MP the depth map alone takes 1.85 s (bench below), over the second: the interactive threshold belongs on the quarter-scale preview, which a sixteenth of the pixels make a fraction of a second
- [x] Preset thresholds (absolute or percentile) for batch runs, and an optional low-confidence mask: `threshold` = `auto` (the default), `level` (the absolute `level`, 0.001 by default) or `percentile` (`percentile` percent of the pixels, 30 by default), stored as three keys so that presets merge key by key (a threshold stored as `{ level = ... }` or `{ percentile = ... }`, as first written, merged into an object with both and failed to read back: regression-tested). `auto`, added for the real stacks: Otsu's level on the logarithm of the confidence (N. Otsu, 1979), taken when the pixels below it have depth that follows noise (median distance to the nearest-agreeing of four neighbors a few windows away at least 0.5 frames and four times the pixels above's), the 10th percentile otherwise. A fixed percentile of 30 filled a third of the wasp's canvas (below), whose smooth background is three quarters of it, and left seams and dark specks around its legs; Otsu's level alone filled 79% of a synthetic stack with texture everywhere and cost it 0.07 of SSIM. The mask (one channel, at least 0.5 to mark) forces its pixels low-confidence (tested: a masked square's depth is filled from around, 0.10 frames from the truth)
- [x] Outputs: the composite, a 16-bit depth map and the confidence map: `DepthMap::depth_u16` (the frame index scaled, 0 for the first frame, 65535 for the last) and `confidence_u16` (`c / (c + level)`, 0.5 at the threshold); the engine keeps them as the output's `depth` and `confidence` maps (16-bit TIFF in the cache), and `output.save` writes any map with `map` (profile `untagged` required: maps are data)
- [x] Tests: depth correlates with ground truth, deltaE near zero, fast threshold changes (`crates/stack/tests/depth.rs`, `memory.rs`): on a textured backdrop on a sloped, undulating depth at camera scale, the depth map's correlation with the truth is 1.000 clean and 0.999 noisy (mean error 0.011 and 0.068 frames; pass 1 alone 0.996 and 0.984); on `scene::textured` (flat discs, thin bristles) 0.63 and 0.63; mean CIEDE2000 against the truth 0.19 on the sloped stack, and below the pyramid's and the weighted average's on clean layered stacks (1.67 against 1.98 and 3.08 textured, 1.02 against 1.11 and 1.62 smooth); against the weighted average on layered stacks, higher SSIM on the textured backdrop (0.929 to 0.961 against 0.896 to 0.922) and less halo everywhere (0.074 to 0.093 against 0.119 to 0.129); the pyramid stays sharper (0.955 to 0.981) where near and far detail overlap, and the depth map's flat-region noise is one or two frames' (0.0068 against the pyramid's 0.0039 on noisy stacks). ### 3.6 Wavelet method *(plan first)*

### 7.3 Browser build *(optional)*

- [x] wasm32 build with eframe's web backend and WebGPU, with a CPU fallback on a Web Worker pool: the desktop app's library built for `wasm32-unknown-unknown` with threads (atomics and shared memory, the standard library rebuilt on the fuzz targets' nightly), started on the page by `apps/florastack/src/web.rs`, drawn with WebGPU or WebGL; florastack-core supplies what the standard library can't there (`fs`, an in-memory file system; `thread`, Web Workers on shared memory, and rayon's pool on them; `time`; `sync`, locks that spin on the main thread; `process`); the engine runs its jobs on `LaneExecutor`'s workers and stacks on WebGPU through a GPU worker (`crate::webgpu`) when the device passes the self-test, on the CPU's workers otherwise. Files come from the file input and drops into `/files`, exports leave as downloads from `/downloads`, and `window.florastack.dispatch` runs engine commands from the page's scripts. Book: [In the browser](../book/src/user/browser.md), [The browser build](../book/src/dev/web.md)
- [x] OPFS-backed `TileStore`, capture disabled, and a clear message when a stack needs more memory than the browser has: the browser's `TempFileStore` keeps its tiles in the origin-private file system through a storage worker (`crates/core/src/opfs.rs`), which also removes what closed pages left; the Capture and Batch tabs, opening and saving projects elsewhere, recent projects and the control channel are left out; files beyond half of the page's 4 GiB are refused, and a stack that wouldn't fit beside them stops before it starts, each with a message that says how much it takes and what to do (`compute::check_memory`)
- [x] Cross-origin isolation headers (COOP and COEP) in the Dockerfile's server config and documented for other hosts; `cargo xtask web`: the root `Dockerfile` builds the site and serves it with nginx (`packaging/web/nginx.conf`, unprivileged, base images pinned to digests), or serves a site built already (`--build-context site=…`); `packaging/web/README.md` gives the headers with nginx, Apache, Caddy, Netlify and Cloudflare Pages examples; `cargo xtask web` builds the site (`--serve`, `--test`, `--clippy`, `--dev`), and a test checks that every config sends the headers
- [x] A headless browser test stacks a 20-frame synthetic stack: `cargo xtask web --test` gives the page 20 frames of a layered scene (the engine's `web_stack` example) through its file input, aligns and stacks them by the pyramid in headless Edge or Chrome (Playwright's library, `apps/florastack/tests/web/stack.mjs`), downloads the output and compares it with the same stack stacked natively. Locally, in headless Edge on Windows with WebGPU, over two runs: frames added in 0.9 to 2.3 s, aligned in 2.2 to 2.5 s, stacked on WebGPU in 1.0 to 4.2 s and on the CPU's 16 threads in 0.5 s; 88.3 dB (WebGPU) and 104.5 dB (CPU) against the native stack.
